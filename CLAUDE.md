# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A barangay (Philippine local government unit) case/records management system: residents file reports, blotters, document/service requests, and emergency SOS alerts; barangay staff (secretary, VAWC desk, police, admin) handle intake, mediation scheduling, analytics, and account approvals. Laravel 12 backend, Inertia.js + React 19 frontend (no separate API/SPA split — pages are server-routed).

## Commands

Backend (PHP):
- `composer install` — install PHP deps
- `php artisan migrate` — run migrations (SQLite by default, `database/database.sqlite`)
- `php artisan db:seed` — local demo data via `DatabaseSeeder`: barangay "San Nicolas", one account per role (phones `09170000001`–`05`, password `password`), document types and assets. Safe to re-run; refuses to run in production. For a real first admin use `php artisan admin:create-root`.
- `composer test` / `php artisan test` — run PHPUnit suite (Feature + Unit); `php artisan test --filter=TestName` for a single test
- `vendor/bin/pint` — format PHP (Laravel Pint)

Frontend (JS):
- `npm install`
- `npm run dev` — Vite dev server (HMR)
- `npm run build` — production build

Full local stack (server + queue worker + log tail + Vite, all at once):
- `composer dev`

Tests live in `tests/Feature` (auth flow, role access, case desks, data protection, report scoping, case numbering, pagination, time zone, audit logging, SMS delivery, document templates, demo seeding) and run on in-memory SQLite. Existing tests create users with the `Tests\Concerns\CreatesUsers` trait (`makeUser($role)`, which expects `$this->barangay`); `User::factory()` (with `->role(Role::X)` and `->unverified()` states) also works. The other model factories are still empty stubs.

## Architecture

**Role-based routing, not permission flags.** Roles are the `App\Enums\Role` enum, and `users.role` is cast to it, so compare with cases (`$user->role === Role::Secretary`), never strings, and use `->label()` or `->value` when putting a role in text. `routes/web.php` defines four separate route groups by prefix (`resident`, `secretary`, `vawc`, `admin`), each guarded by the `role:<name>` middleware (`EnsureUserHasRole`), which aborts 403 for any other role. There's a fifth role, `barangay_police`, which has no portal at all: those accounts only receive SOS alerts by SMS, and the staff login refuses them. When adding a route for a role, add it inside that role's existing group in `web.php`, not as a new top-level route — and mirror the corresponding `Layout` in `resources/js/Layouts/`.

`Role::homeRoute()` (wrapped by `User::homeRoute()`) is the single source of truth for where each role lands after login — update it when adding/renaming a role's landing page. It is used both by `AuthController` and by the `guest` middleware redirect in `bootstrap/app.php`, which also sends signed-out visitors to `/secretary`, `/vawc` or `/admin` pages to the staff login instead of the resident one. Residents sign in at `/login`; staff (`Role::staff()`) at `/portal/secure-login`.

**Confidential data at rest.** Free text that can hold incident or VAWC details is encrypted with `APP_KEY` through `encrypted` model casts: `reports.description`, `blotter_records.incident_description`, `blotter_records.complainant_name` / `receiver_name` (typed-in party names), `mediation_schedules.notes` and `vawc_details.confidential_notes`. These columns can't be searched or sorted in SQL, and must be read through the model, never `DB::table`. Sensitive uploads (resident ID photos, selfies, report attachments) go through `App\Services\SecureFileStore`, which encrypts them on the private disk (`*.enc` files) and serves them only from authorized controller actions. Don't use `->store()` or `Storage::response()` for them. `php artisan files:encrypt-sensitive` converts any file stored before encryption. Losing or changing `APP_KEY` makes all of this unreadable; to rotate it, move the old key to `APP_PREVIOUS_KEYS`. `LoginRequest::authenticate()` checks credentials and rate limits failures (5 per phone number + IP) without starting a session, so each login action applies its portal rules before calling `Auth::login`.

**Inertia page resolution.** `resources/js/app.jsx` globs `./Pages/**/*.jsx`. A controller's `Inertia::render('Secretary/BlotterManagement')` maps directly to `resources/js/Pages/Secretary/BlotterManagement.jsx` — filenames and folder names must match the string passed to `Inertia::render` exactly, including case. Layouts are applied centrally: the `layout` option in `app.jsx` maps each `Pages/<Role>/` folder to that role's `Layout` (e.g. `Layouts/SecretaryLayout.jsx`), so pages must not wrap themselves in a layout — return a fragment instead. A page can override this by setting its own `Page.layout`.

**Shared Inertia props.** `app/Http/Middleware/HandleInertiaRequests.php` shares `auth.user` (id, full_name, role, barangay) and flash `success`/`error` messages on every request — read these from Inertia props in pages rather than re-fetching user/session state.

**Domain model shape.** Core models: `User` (has `role`, `barangay_id`), `Barangay`, `BlotterRecord` (+ `MediationSchedule`, `VawcDetail` for VAWC-flagged cases), `Report` (resident-filed incidents, including SOS/emergency), `DocumentRequest` / `DocumentType`, `ServiceRequest`, `BarangayAsset` (resources secretaries assign to service requests), `Attachment` (polymorphic-ish file uploads tied to `uploaded_by`), `SystemLog` (audit trail, actor-tracked — log every staff write action, inside the same `DB::transaction` as the change it records; see `AdminController::auditLogs`). `system_logs.barangay_id` is nullable for citywide actions. Sign-ins, sign-outs, failed sign-ins and lockouts are logged by `App\Listeners\LogAuthenticationEvents`. Never put a VAWC report's or case's details in a log description, since the citywide admin reads the audit trail. Models use explicit `$fillable` lists, not `$guarded = []`, so add new columns to `$fillable` or `create()`/`update()` will silently drop them.

**Blotter vs VAWC split.** `BlotterController` (secretary) and `VawcController` (VAWC desk) both manage blotter records with the same route shapes (`blotters`, `blotters/create`, `case-history/{id}`, `mediation-calendar`, `cases/{id}/schedule-mediation`), rendering each desk's own pages. The case workflow itself (create page, resident search, case history, PDF, mediation scheduling and notes, calendar, resolve/escalate/reopen) lives once in the abstract `CaseDeskController`, which both extend. Everything that differs between desks (which cases they see, page folder, route prefix, log wording) is in the `App\Enums\CaseDesk` enum, so fix workflow bugs there once, not per desk. The subclasses only keep what is genuinely desk-specific: list, export, filing (`FileBlotterCase` / `FileVawcCase`) and VAWC analytics. A VAWC case is one with a `VawcDetail` record, created only when the VAWC desk files the case (`App\Actions\Vawc\FileVawcCase`); it is then visible to the VAWC role only. Secretary cases cannot be reclassified as VAWC. Residents can flag their own incident reports as VAWC (`reports.is_vawc`), which routes the report to the VAWC desk only (`Report::scopeVisibleTo`, `ReportPolicy`). A report belongs to the barangay it was filed in (`reports.barangay_id`, set on create from the reporter's barangay and kept if they move), so scope reports by that column, never through `users`. 
**Time zone.** The app runs in `Asia/Manila` (`config/app.php`; MySQL session `+08:00` in `config/database.php`). Timestamps are stored as Manila wall-clock time, times typed into forms (e.g. `datetime-local` hearing times) are Manila time, and Carbon's `now()`/`today()`, server-formatted dates (PDFs, exports, certificates) and the scheduler all use Manila time. Pages receive dates as UTC ISO strings and should display them with `new Date(...)`; date-only fields are cast as `date:Y-m-d` so they arrive as plain `YYYY-MM-DD`. Don't create NOT NULL `timestamp` columns: on MySQL/MariaDB with `explicit_defaults_for_timestamp` off (the XAMPP default), the first one in a table silently gets `ON UPDATE CURRENT_TIMESTAMP`. Use `dateTime()` for dates the app sets itself.

**Case numbers** come from `BlotterRecord::generateCaseNumber($prefix, $barangayId)`, which must run inside the filing transaction: it locks and increments the matching `case_number_sequences` row (per barangay, prefix and year). BLT and VAWC are numbered separately, so neither desk can infer the other's volume, and numbers are never reused after a case is deleted. Never compute numbers by counting cases.

**Large lists.** Index pages paginate with `self::PER_PAGE` (use a named page parameter when a page shows several lists, as Resident Tracking does). Calendar pages load one month at a time via `?month=YYYY-MM` (`Controller::calendarMonth`/`calendarRange`, `Components/calendarMonth.js`). Pickers over potentially large sets use `Components/SearchAutocomplete` against a JSON search endpoint (`ResidentAutocomplete`, `PendingReportPicker`) instead of loading every option into a dropdown.

**Emergency SOS flow.** `ReportController::storeEmergency` hands off to the `App\Actions\Report\TriggerSos` action, which reverse-geocodes the location, checks it against the barangay boundary, creates the `Report` with its audit entry, fires `App\Events\SosTriggered` (`ShouldBroadcastNow`, broadcasts on the `emergency-alerts` channel via Reverb/Pusher), and dispatches one `App\Jobs\SendSmsJob` per barangay police officer. SOS belongs to the secretary desk only: only `SecretaryLayout.jsx` shows the live alert, and `Report::scopeVisibleTo`/`isHandledBy` give the VAWC desk nothing but resident-flagged VAWC reports, so it never lists, opens or acknowledges an SOS. This is deliberate. Broadcasting auth is in `routes/channels.php`. If SOS changes are needed, all three pieces (event, queued job, channel) usually need to move together.

**SMS.** Every SMS (SOS alerts, account approval/rejection, document-ready notices, the daily hearing reminder in `routes/console.php`) is sent by dispatching `SendSmsJob($phone, $message)`, one job per recipient, so queue retries never re-text someone who already got the message. Never call `PhilSmsService::sendSms()` from request code. The service makes one attempt: it returns false for permanent failures (no token, invalid number, provider rejection), and the job then gives up; it throws `SmsDeliveryException` for temporary ones, and the queue retries. With `SMS_ENABLED=false` (the default) messages are only written to the log. Delivery needs a queue worker running (`composer dev` starts one).

**Account approval flow.** Resident self-registration (`/register`) creates unverified accounts (`is_verified = false`, with `id_photo_path`/`selfie_id_path` uploads); secretaries approve/reject via `secretary/account-requests` (`AccountController::approve/reject`, backed by `App\Actions\Account\*`). Secretaries also create `barangay_police` accounts directly (`AccountController::storePolice`) and edit/delete residents and police in their barangay. `AuthController` only handles sign-in, registration and sign-out; citywide staff accounts (secretary/vawc/admin) are managed by `AdminController`. When deleting a resident, delete the row first and then call `User::deleteVerificationDocuments()` so a failed file delete never leaves a user without evidence.

**Services layer.** `app/Services/PhilSmsService.php` (SMS, used only by `SendSmsJob`) and `app/Services/OpenStreetMapService.php` (geocoding/mapping — used alongside the `leaflet`/`react-leaflet` frontend deps) are injected into controllers/jobs via constructor DI, not called statically.
